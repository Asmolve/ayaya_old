# Specification

## 1. Общая информация

### Назначение

Проект представляет собой модульную веб-платформу, объединяющую независимые пользовательские сервисы под единым интерфейсом и единой системой авторизации.

Каждый функциональный блок является самостоятельным приложением, которое может разрабатываться независимо от остальных компонентов системы и использовать собственный стек технологий.

Основная цель проекта — практическое изучение проектирования крупных распределённых систем, современных архитектурных подходов и технологий.

Дополнительные цели:

* создание проекта для портфолио;
* использование платформы в личных целях;
* возможность использования сторонними пользователями после публикации.

---

# 2. Архитектурные принципы

## Core

Core является единственной обязательной частью системы.

Он отвечает за:

* авторизацию;
* регистрацию пользователей;
* выдачу JWS;
* глобальные права доступа;
* маршрутизацию;
* регистрацию модулей;
* централизованные настройки;
* управление подключёнными сервисами;
* управление scheduler;
* взаимодействие между модулями.

Core не содержит бизнес-логики модулей.

---

# 3. Модули

Каждый модуль является самостоятельным приложением.

Модуль:

* имеет собственный backend;
* имеет собственный frontend;
* имеет собственный API;
* имеет собственную бизнес-логику;
* имеет собственные таблицы в PostgreSQL;
* может использовать собственные технологии;
* разворачивается в отдельном контейнере.

Примеры модулей:

* Finance Calendar
* Shopping List
* Gallery
* Anime Tracker
* Notes
* Todo

Архитектура допускает разработку модулей различными разработчиками, включая ИИ-агентов.

---

# 4. Поддерживаемые технологии

Core:

* Ruby
* Sinatra

Reverse Proxy:

* NGINX

Database:

* PostgreSQL

Cache:

* Redis

Контейнеризация:

* Docker

Оркестрация — определяется позднее.

Модули могут использовать любые языки программирования.

Например:

* Go
* Python
* Ruby
* Rust
* Node.js

при условии соблюдения контрактов взаимодействия.

---

# 5. Авторизация

Авторизация выполняется исключительно Core.

После успешной аутентификации Core выдаёт JWS.

Все модули доверяют JWS Core и не реализуют собственную систему авторизации.

---

# 6. Пользователи и права

Глобальные роли:

* Guest
* User
* Admin

Каждый модуль может вводить собственные роли.

Локальные роли действуют исключительно внутри конкретного модуля и не влияют на глобальные права пользователя.

---

# 7. Frontend

Каждый модуль предоставляет собственный пользовательский интерфейс.

Core отвечает только за:

* меню;
* навигацию;
* авторизацию;
* переход между модулями.

---

# 8. API

Поддерживаемые способы взаимодействия:

* REST
* WebSocket

Опционально:

* gRPC
* GraphQL

Core определяет общие требования к API.

---

# 9. Взаимодействие модулей

По умолчанию взаимодействие происходит через Core.

В дальнейшем допускается событийная архитектура с использованием брокера сообщений.

Предпочтительным вариантом рассматривается Kafka.

Каждый модуль также может иметь собственную внутреннюю систему событий.

---

# 10. Хранение данных

Используется единый экземпляр PostgreSQL.

Каждый модуль использует собственный набор таблиц.

Модули не должны обращаться к таблицам друг друга напрямую.

Обмен данными осуществляется только через API либо события.

---

# 11. Scheduler

Система должна поддерживать выполнение фоновых задач.

Примеры:

* проверка новых серий;
* синхронизация календарей;
* обновление галереи;
* отправка уведомлений.

---

# 12. Интеграции

Core хранит информацию обо всех подключённых внешних сервисах.

Пример:

Google Calendar подключается один раз и может использоваться несколькими модулями одновременно.

Аналогично могут использоваться:

* Google Drive
* Dropbox
* Telegram
* Discord
* GitHub
* другие сервисы.

---

# 13. Развёртывание

Каждый модуль разворачивается отдельно.

Обновления должны быть:

* бесшовными;
* откатываемыми;
* независимыми от остальных модулей.

При отключении или удалении модуля NGINX должен отдавать статическую страницу с объяснением причины недоступности.

---

# 14. Масштабирование

На первом этапе высокая нагрузка не рассматривается.

Архитектура должна предусматривать возможность дальнейшего горизонтального масштабирования без серьёзного изменения компонентов.

---

# 15. Нефункциональные требования

* модульность;
* независимость модулей;
* возможность написания модулей на разных языках;
* единая авторизация;
* единая система пользователей;
* единая точка входа;
* минимальная связанность компонентов;
* возможность независимого деплоя;
* возможность независимого обновления;
* возможность независимого тестирования.

---
